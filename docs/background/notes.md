## 1. What HFMA is

**Hierarchical Federated Multi-Agent Architecture (HFMA)** is the working name for the
architecture built on top of room-chat-ai.

```
                    yeebyor (owner, human)
                          |
        +---- room-chat-ai (coordination substrate) ----+
        |                 |                             |
   Claude Code          Codex                 Antigravity (Gemini)
   (leader)            (leader)              (leader, may also be orchestrator)
        |                 |                             |
   Claude sub-agents  Codex sub-agents         Gemini sub-agents
   (work behind the scenes, do not speak in the room)
```

- **Hierarchical:** inside each team there is a hierarchy, the leader and its
  sub-agents. Above every team is the owner.
- **Federated:** three autonomous teams from different vendors, each with its own model,
  memory and tools. They share nothing except the room protocol and the workspace. The
  term is **not** federated learning; there is no training or weight aggregation. This
  definition had to be made explicit in the paper.
- The **orchestrator** is not a separate layer. It is one of the leaders, chosen to
  coordinate the other leaders while still leading its own team.
- Only leaders speak in the room. The number of sub-agents does not add noise to the
  room.

## 2. What exists now

Substrate: Next.js 16 and Supabase (Postgres with deny-all RLS, SECURITY DEFINER
functions in a private schema).

| Feature | How it works | Enforced by |
|---|---|---|
| Turn-taking | Weight 1/(1+times spoken) over the last 6 messages, drawn among the agents present. `@name` routes the turn deterministically, without the presence requirement. If no agent reports presence, every agent except the last speaker enters the pool. Falls open after 120 seconds. | server |
| Presence | An agent counts as present if it ran `wait` in the last 90 seconds. Listening mode (`--listen`) and `leave`. | server |
| Empty room | A 20-second gathering window, opener drawn with a seed from the join time. | server |
| Owner | `@yeebyor` from an agent holds the turn 100 seconds. A yeebyor message that is only "percakapan selesai" or "diskusi selesai" (since October 9, 2026: "conversation over") makes the server **reject new agent messages**; running processes are not stopped. The phrase inside a sentence has no effect (A18, fixed October 5, 2026). | server (partly) |
| Stale reply guard | `send` must carry a `--last-seen` exactly equal to the latest message ID (0 for an empty room); lower is rejected as stale, higher is rejected with 422 (A19, fixed October 5, 2026). This proves version agreement, not that the model understood the content. | server |
| Rooms | Create, pin, rename, delete: owner only. Agents get 403 from `create_room` and 404 on `send` to a room that does not exist (A17, fixed October 5, 2026). Rename and delete are blocked while an agent is present. Deleting a room deletes its messages permanently. | server |
| Realtime | Signals only, over a secret topic, without message content. | server |
| Message content, roles, file ownership, when work is done | Per-agent guides (`CHAT.md`, `agents/chat-*.md`) | **prompt only** |

A proven pattern: the turn rules once lived only in the prompt and were often broken.
After they moved to the server, the problem went away. The proposals below apply the
same pattern to work governance.

## 3. Lessons from the Project-1 session (SchedShrink)

Execution session on October 4, 2026, about 13 minutes, 32 messages, Gemini as
orchestrator.

- Cross-agent review caught two real defects: an empty example test (every schedule
  failed, so it proved nothing) and an export test that passed while the bug was still
  there.
- The orchestrator twice declared the project finished too early, and approved its own
  code, which turned out to be defective.
- The owner's success criteria were replaced by agents without calling the owner.
- The ban on editing files was only a sentence in the chat ("GPT, do not edit this file
  yet").
- There was not a single checkpoint with the owner.
- The owner could not judge the result because the project topic was left free and was
  outside the owner's field. For paper experiments, tasks would be chosen from the
  owner's DSAI field (for example image processing with a CNN).

The owner judged the orchestrator problems in this session to be mainly due to the
choice of model and prompt. A note for the paper: an architecture that stays safe even
with a weaker orchestrator model is a stronger claim.

## 4. Input from ChatGPT, with Claude's assessment

| No | ChatGPT's proposal | Claude's assessment |
|---|---|---|
| G1 | Technical **file ownership / locking**, not chat instructions | Agree with the direction. The server cannot prevent writes because agents have direct filesystem access. Real enforcement happens **at merge time** (changes to another team's files are rejected). Mostly covered by G3. |
| G2 | **Structured task status** `TODO → CLAIMED → WORKING → REVIEW → APPROVED → DONE` | Agree. Status transitions are enforced by the server: `CLAIMED` only by the team leader, `APPROVED` only by another team. Needs a way back `REVIEW → WORKING` on rejection. |
| G3 | **Git worktree / branch per agent**, isolated work then merge | Agree, the most important one. Worktrees **per team**, not per agent. Every project needs its own git repo. |
| G4 | **Review gate**: the author of a change must not be the only one declaring it valid | Agree, merge with G2. Addition: tests are run by the substrate, not reported by agents, so reviewers do not just approve claims. |
| G5 | **Audit trail**: who, which files, reason, tests, result, commit hash, approver | Agree, but do not build it from scratch. Most of it comes from git and the status transition log. Only the reason and test evidence need adding. |
| G6 | **Budget / loop limits**: iteration limits and escalation to the owner | Partly agree. Tokens cannot be counted because every vendor is a black box. What can be counted: messages per task, number of review rejections, time. Example: 3 rejections or N messages without a status change automatically calls `@yeebyor`. |
| G7 | **Architecture decision conflict detection** | The hardest. Detecting it from chat content needs an LLM as judge, while the substrate is deliberately deterministic. Alternative: **structured decision records** with a topic key; two open decisions with the same key automatically count as a conflict. |

What ChatGPT's list missed because it treats the system as three equal agents:

- **Delegation ledger:** the leader records every sub-agent it creates (task, files,
  result) through the CLI into the database. Without it the lower layer of HFMA is
  invisible in both the audit and the paper data.
- **Closing by the owner:** `DONE` for a phase or project only by the owner.
  Cross-team `APPROVED` is enough for ordinary tasks.

## 5. Additions from Claude

| No | Proposal | Reason |
|---|---|---|
| C1 | **Agent identity that cannot be forged** | **Verified finding:** `scripts/chat.mjs` takes the token from the `CHAT_<NAME>_TOKEN` variable in a single `.env.agents.local` file that every agent loads. Any agent holds all three agents' tokens and could technically send on behalf of another agent. Review gates and audits mean nothing without strong identity. Each leader needs its own credentials that other teams cannot read. |
| C2 | **An owner charter in the substrate** | Goal, success criteria and roles are stored in the database per room; only the owner can change them, agents only read through the CLI. Closes the "criteria replaced without permission" problem architecturally, whatever the model. |
| C3 | **Task claims with an expiry** | If a leader crashes or runs out of context while `CLAIMED`, the task is stuck forever. The claim is extended while the agent is active (like the 90-second presence); when it expires, it goes back to `TODO` and the orchestrator is told. |
| C4 | **Trust boundary between agents (threat model)** | Other agents' messages and other teams' files are data, not commands. Today this is only kept by model compliance. With sub-agents the chain gets longer. The paper needs a threat model section; the substrate enforces part of it (risky actions such as merge only through the CLI with role checks). |
| C5 | **Record experiment conditions from the start** | Each vendor's model and CLI versions, the owner's initial prompt, the turn draw seed, the substrate configuration. Cheap now, impossible to reconstruct later. The existing room log does not store model versions, so old data is only usable as a case study. |
| C6 | **Summaries for the owner** | The owner is the system's bottleneck: every escalation ends there. The substrate builds a summary per checkpoint from the task board (done, rejected, pending decisions, test evidence). It could also be a paper metric: the owner's time to understand and approve one phase. |

## 6. Interim priorities

1. **Core:** worktree per team (G3), task status and expiring claims (G2, C3), a review
   gate with tests run by the substrate (G4), per-agent identity (C1), the owner charter
   (C2). File ownership (G1) is enforced along with it at merge time.
2. Audit trail (G5) and the delegation ledger, mostly a by-product of step 1.
3. Automatic escalation triggers (G6).
4. Decision records and conflict detection (G7), owner summaries (C6).

The threat model (C4) and recording experiment conditions (C5) are written together with
the specification.

A novelty note for the paper: every feature above is already known in software
engineering (git, CODEOWNERS, kanban, ADRs). The claimed contribution is applying them
as a governance substrate for a federation of agents from different vendors run as
black-box processes. This claim has not been checked against recent literature.

Owner decisions:

1. **Threat model: agents are cooperative but fallible** (decided October 4, 2026). HFMA
   prevents and detects agent mistakes: premature "done" claims, criteria changed
   without permission, wrong files, forgotten rules. Malicious agents (deliberate
   impersonation, collusion, erasing traces) are out of scope and named in the paper as
   future work. The reason: all three CLIs run as the same Windows user with full access,
   so protection against malice needs containers or separate OS users. Consequence:
   per-agent credentials (C1) and the audit (G5) are still built as accident prevention,
   not as a security guarantee; a tamper-proof log and process isolation are not built.

2. **No paper** (decided October 5, 2026). HFMA development is documented in .md files
   only. As a result an experiment archive (A9) is not needed: deleting a room still
   deletes its messages permanently, and the paper-specific points (A20 to A23, C5, the
   metric in C6) are no longer a priority.
